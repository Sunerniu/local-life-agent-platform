# 店铺详情二级缓存

`GET /shop/{id}` 依次访问 Caffeine → Redis → MySQL，保持原接口响应。
本地命中不访问 Redis；本地缓存按访问频率和近期使用情况淘汰，适合热点店铺。
本地存储 JSON 快照，避免可变 Shop 对象在请求间共享。空结果也会缓存，Redis 使用空字符串，修复原实现写入 null 的问题。

## 配置

- `SHOP_CACHE_MAXIMUM_SIZE`：本地最大条目数，默认 10000。
- `SHOP_CACHE_TTL`：本地写入后过期时间，默认 `30s`，持续访问不会延长。
- `SHOP_CACHE_CHANNEL`：失效频道，默认 `hmdp:shop:invalidate:<Redis数据库编号>`。同一业务的实例必须一致，不同环境应隔离。
- Redis 保留原 `cache:shop:<id>` JSON 格式和 30 分钟 TTL；不存在的店铺保留 2 分钟 TTL。

## 更新与一致性

店铺资料更新及营业时间条件更新成功后，注册事务提交回调。提交后通过 Lua 原子增加版本、删除 Redis、发布店铺 ID。每个实例订阅频道并删除对应本地条目；回滚不触发失效。

`cache:shop:version:<id>` 是每个更新过的店铺的持久版本计数器。回源前读取版本，写入 Redis 时以 Lua 校验，防止旧查询在更新后重新写入缓存。不要单独清除此版本键，否则会破坏在途加载的版本校验。本地加载与通知使用固定数量的分片锁，防止本地失效后旧查询再次写入，也合并同实例的并发回源；不提供跨实例回源互斥。

这是最终一致性方案：Pub/Sub 不保存离线消息，通知丢失时本地缓存通过短 TTL 收敛。Redis 删除/广播失败会向调用方报错，但此时数据库事务已提交；本实例仍会清理本地缓存。此故障下 Redis 旧值可能保留至原 Redis TTL，不能宣称由本地 TTL 保证收敛。需要可靠投递/强一致性的场景应增加事务 outbox 和重试消费者。

仅覆盖上述两个应用更新入口；直接 SQL、更改 Redis、继承的通用 CRUD 或旧的演示缓存方法不会自动广播。现有逻辑过期预热方法使用不同 JSON 格式，不应与默认详情查询在同一 key 上混用。当前 Lua 沿用项目单机 Redis 配置，未适配 Redis Cluster 多键 hash slot。

## 验证

运行 `mvn test`。`ShopCacheTest` 使用模拟 Redis 验证查询顺序、负缓存、实例失效、事务提交/回滚和并发回填。它不代替真实 Redis 多进程和数据库集成测试。
